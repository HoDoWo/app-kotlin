# Translations (i18n)

Epic #169. English is the default language (`res/values`); Italian is in `res/values-it`.
Spanish (#233) and Catalan (#234) will be `values-es` and `values-ca`.

## How the app language works

- The user picks it in **Settings → Language** (#210); "System default" follows the phone.
- `AppLanguage` applies it with AppCompat per-app locales (#235): Android 13+ keeps it in the
  system (it also appears in the system's per-app language settings), older versions in AppCompat.
- The choice is stored in DataStore with the other preferences (#211).
- The AR scan asks the backend for answers in the app language.

## Writing a translatable screen

- Every text the user sees is a resource: `stringResource(R.string.…)`, never `Text("…")`.
- Counts use plurals: `pluralStringResource(R.plurals.…, count, count)`; never build
  "1 item" / "2 items" in code.
- Names, numbers, prices and dates are format arguments (`%1$s`, `%1$d`), never glued to a sentence.
- Keys are named by screen and purpose: `profile_sign_out_confirm_title`, `auth_error_network`.
- Texts needed in click handlers (Toasts) are read with `stringResource` in the composable
  before the handler, not with `context.getString` (Compose lint).
- View models and repositories may keep English texts for logs and tests; the UI maps the
  ones it shows to resources (see `ui/AuthMessages.kt`).
- Every new key goes in `values/` **and** `values-it/` (lint fails on a missing translation).

## The check

`HardcodedStringsTest` (unit tests) fails when a translated file contains a hard-coded text
(`Text("…")`, `contentDescription = "…"`, `title = "…"`, Toasts, `if (…) "…" else "…"`).
Each extraction slice adds its files to `TRANSLATED_FILES`:

| Slice | Files | Status |
|---|---|---|

| #231 Home, Chat, Camera, Manuals, Guides | – | to do |
| #232 Market, Product, Cart, Checkout, Listings, Forum, Messages | – | to do |

The AR screens use `strings_ar.xml` (EN + IT) and `ArText` keys from the view model.
